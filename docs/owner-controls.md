# Owner controls and recovery deployment

This is an operational deployment checklist, not evidence that production has been activated. Current release status and business decisions are in [final-stabilization.md](final-stabilization.md). The demo remains stopped.

## Access and credential escrow

`owner_control.php` and `/api/v1/owner-control` require an active, currently assigned SuperAdmin **and** a verified owner ID in protected server configuration. A role override or forged cached role does not grant owner access. There is no application API for editing that configuration. Account 1 ownership is awaiting Houssein's confirmation; account 11 remains unchanged.

Provision `CLMS_OWNER_CONFIG_FILE` as an absolute path outside every web root and outside the repository. Use a secret store or an ACL-protected file readable only by the application service and approved recovery administrators. Verify that the database service cannot read it. The application DB identity must have only application-schema privileges: no global ALL, FILE, grant option, or role grants whose effective privileges cannot be verified. The current source connection is `root@localhost`; production escrow is blocked by this boundary check. The process-owner inspection returned access denied, so OS key isolation is **not proven**.

Protected configuration fields (names only; never paste their values into documentation/chat):

- `owner_verified`, `owner_ids`: set only after human ownership and emergency access verification.
- `escrow_enabled`, `escrow_user_ids`: explicitly eligible internal accounts; owner accounts are excluded from employee recovery.
- `active_key_id`, `escrow_keys`: key IDs mapped to independently generated 32-byte keys, base64 encoded. Retain old keys until all associated envelopes have been migrated and restore tested. Back up keys through a separate encrypted recovery process controlled by Houssein, not in the application SQL dump.
- `owner_totp_keys`: each verified owner's independently generated authenticator secret, base64 encoded, at least 20 bytes. Enroll through a secure local/secret-manager channel. No enrollment secret is exposed through normal APIs. Six-digit RFC 6238 codes use 30-second steps with a one-step drift window. Replay/throttle state is held in the protected configuration's adjacent `.mfa-state` file, under an exclusive lock. Five bad/replayed attempts block that owner factor for 15 minutes.
- `key_isolation_verified`: deployment evidence for the file/secret-store boundary. This flag does not override the restricted DB-grant check.
- `immutable_audit_verified`, `audit_url`, `audit_bearer`, `audit_receipt_public_key`: enable only after verifying the external append-resistant audit service and its retention. Production requires HTTPS. The append contract is POST of non-secret event metadata; HTTP 201 with a base64 RSA/SHA-256 signature over `event_id|sha256(exact_request_body)`. A signed response authenticates acknowledgement; **it does not by itself prove provider immutability**. That infrastructure evidence is still required. B2 is not automatically an implementation of this append API.

Authentication remains `password_hash`/`password_verify`. AES-256-GCM envelopes have random 12-byte nonces and 16-byte tags; authenticated data binds account ID, credential fingerprint, format version and key ID. Normal user lists, API responses, exports and audit snapshots exclude envelope/password material. SQL backups contain only ciphertext for escrow; key material is separate. An owner database hash replacement alone cannot satisfy the separately protected second factor.

An eligible credential is enrolled on a verified sign-in or atomically with an approved password change. It cannot be reconstructed from an existing hash. Accounts 3, 4, 5, 6 and 11 have `credential_recovery_required=1`: password changes fail safely until a verified owner recovery setup is available. Their credentials and session versions have **not** changed. Do not rotate them until the mapping/owner/access conditions approved by Houssein are satisfied. No permission, historical attribution or operational owner is moved implicitly.

Recovery requires current owner authorization, sign-in within 15 minutes, the owner's current password, and an unused authenticator code. Re-authentication uses the existing login throttle. Every authorized reveal writes a local attempt event, obtains immutable external acknowledgement, rechecks actor/target revocation, then writes the local reveal event before returning the credential. If any step fails, no credential is returned. External events identify an authorized disclosure attempt, not proof that a human read the response. Actor, target, timestamp, IP and a session fingerprint are recorded; passwords, OTPs, raw session IDs and keys are excluded.

The dedicated reveal response uses no-store headers. The UI clears the value after 20 seconds, on blur, visibility change, close or navigation; late responses cannot repopulate a closed view. It never writes the value to local/session storage, the URL or the clipboard. Browser/OS memory cannot be cryptographically erased by JavaScript; an authorized person can still remember/copy what they see. Production recovery requires HTTPS.

## Incident center

The owner view groups incidents by workflow/action/error category, with affected-user counts, occurrence counts, first/last timestamps and severity. Detail retains safe user identity/role, request ID, business IDs, observed rollback state and correlated retry result. Resolution status and notes use revision checks and audited writes. Expected input/eligibility failures are LOW; authorization failures are MEDIUM; unexpected application failures HIGH; rollback/database integrity failures CRITICAL. Sanitized user-visible errors are retained, while raw request bodies, exception stacks, authorization headers and credentials are excluded. Secret-bearing request fields/cookies are scrubbed before recording.

The main API captures failures after the failed response, using a separate database connection. It never commits a cargo/financial transaction. Persistence failure falls back to a non-secret diagnostic request reference; a database outage cannot be recorded in the same unavailable database. Browser runtime/network reporting submits only a controlled failure code and page name, with session rate limiting and no exception text. Shared API retries correlate only the same actor/workflow/action/business record; raw-fetch paths can remain `not_observed` rather than inventing a successful retry.

The owner-only high-visibility badge polls every 30 seconds while visible, with no overlapping requests. Background polling does not extend authenticated idle time. There are no real email/WhatsApp alerts or repeated per-validation notifications. The dashboard includes recent successful authentication, recorded failed logins, unresolved/resolved incidents, integration failure counts and credential/security audit events. It cannot notify an offline owner during a complete server outage; off-host monitoring/audit infrastructure remains an operational requirement.

## Sessions and retention

New sessions enforce the approved policy. Enable `CLMS_SESSION_POLICY_ENABLED=1` only with the approved deployment/session-revocation plan to enforce it on pre-policy sessions. Ordinary users: 8-hour idle / 30-day absolute. SuperAdmin, ChinaAdmin and LebanonAdmin are conservatively treated as privileged: 30-minute idle / 12-hour absolute. Sensitive user/configuration writes require recent authentication. Both login paths bind tracked sessions to the actual authenticated database; a cookie from a different database or without this binding is rejected. Password rotation increments `session_version`; a changed credential fingerprint also invalidates a tracked session.

No historical records are deleted by the new retention tools. `retention_holds` supports all-scope or category/reference holds. A hold must not be released without Houssein's explicit release reference. `scripts/retention_sessions.php` defaults to dry-run and removes only expired, explicitly CargoChina-marked session material older than 90 days, while holding its file lock. Shared/unmarked session files are untouched. Empty files are left for PHP GC to avoid an unlink race on Windows. `scripts/retention_logs.php` defaults to dry-run; only recognized dated logs are eligible. New diagnostic/performance/translation logs rotate daily and retain 90 days; general/security/tracking logs retain at least one year. Undated legacy logs remain preserved pending a dated inventory. No production purge or scheduled task was executed.

Business cargo/shipment/financial records and linked evidence retain 10 years; audit history and referenced departed identities retain 7 years; temporary exports 90 days unless attached to a business record. Active matters and holds must not be deleted merely because they are old. Unknown-owner uploads remain excluded. Streamed client downloads require staff retention procedures; server cleanup cannot delete staff copies.

## Encrypted backups and recovery

`scripts/encrypted_backup.php` supports `backup`, `backup-uploads`, `verify`, and isolated SQL `restore`. Run PHP with `-d extension=sodium` (the extension exists here but is not globally enabled). It streams MySQL dump or the uploads tar into libsodium secretstream, sealing a random per-archive key to a recovery public key. No plaintext SQL backup file is created. `verify` authenticates the entire archive, including final-frame/truncation checks. SQL restore authenticates first, then streams into an explicitly named `clms_restore_*` database; production restore credentials must be restricted to that database. Never restore into the live schema. An authenticated archive is not a substitute for verification of restored application records.

Protected environment paths are `CLMS_BACKUP_FILE`, `CLMS_BACKUP_KEY_FILE`, `CLMS_MYSQL_OPTIONS_FILE`, `CLMS_MYSQL_BIN`, and `CLMS_BACKUP_DB`. Backup uses the recovery public key; verification/restore require the private keypair on the isolated recovery host. Generate/custody that recovery keypair off-host under Houssein's control. The MySQL options file contains only the backup/restore service credentials and must live outside web roots/source control. Existing local plaintext rehearsal backups are retained until verified encrypted replacements and owner recovery custody exist; they are not claimed as off-host protection.

Schedule database backups at least every four hours, plus uploads/configuration needed to restore that recovery point. Keep all four-hour snapshots within 35 days, at least 35 daily, 12 monthly and 3 annual generations, and every held generation. `RetentionPolicyService::keepBackups` computes a conservative keep set; it does not delete remote objects. `RPO <= 4h` and `RTO <= 4h` require measured production-style evidence, including application/config/uploads/key recovery, not just SQL import time.

No off-host destination is configured. The proposed company-controlled B2 bucket must use pre-upload encryption, a bucket-restricted upload identity without deletion/retention-bypass privileges, separate Houssein administrative ownership, and verified Object Lock/append resistance. Do not store B2 credentials in SQL, source, logs or documents. No B2 account/bucket was invented or contacted. Before PASS: backup -> encrypted off-host upload -> independent download -> isolated authenticated decrypt/restore -> record/application verification, including retained generations and audit retrieval. The local 74-table encrypted SQL rehearsal does not satisfy this gate.

Technical references: [PHP authenticated encryption](https://www.php.net/openssl-encrypt), [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238), [Backblaze Object Lock](https://www.backblaze.com/docs/cloud-storage-object-lock), [Backblaze application keys](https://www.backblaze.com/docs/cloud-storage-application-keys). Provider guarantees must be verified against the actual account configuration.
